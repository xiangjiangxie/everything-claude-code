# 旁问命令

在任务进行中提出问题并获得即时、聚焦的回答 — 然后继续从上次中断的地方工作。当前任务、文件和上下文不会被修改。

## 使用场景

- 在 Claude 工作时你对某些内容感到好奇，不想打断节奏
- 需要快速解释 Claude 正在编辑的代码
- 想要对某个决策获取第二意见或澄清，而不偏离任务
- 需要在 Claude 继续之前理解某个错误、概念或模式
- 想问与当前任务无关的问题，而不需要开始新会话

## 用法

```
/aside <你的问题>
/aside 这个函数实际返回什么？
/aside 这个模式是线程安全的吗？
/aside 为什么我们在这里使用 X 而不是 Y？
/aside foo() 和 bar() 之间有什么区别？
/aside 我们刚添加的 N+1 查询需要担心吗？
```

## 流程

### 第 1 步：冻结当前任务状态

回答任何问题之前，先在心里记录：
- 当前活跃的任务是什么？（正在处理哪个文件、功能或问题）
- 调用 `/aside` 时正在进行哪个步骤？
- 接下来即将做什么？

旁问期间不要触碰、编辑、创建或删除任何文件。

### 第 2 步：直接回答问题

以尽可能简洁但完整且有用的形式回答问题。

- 先给出答案，而非推理过程
- 保持简短 — 如需完整解释，提议在任务完成后深入
- 如果问题涉及正在处理的当前文件或代码，精确引用（文件路径和行号）
- 如果回答需要读取文件，读取即可 — 但仅读取，绝不写入

格式化响应为：

```
ASIDE: [简要重述问题]

[你的回答]

— 回到任务：[正在做的事情的一行描述]
```

### 第 3 步：恢复主任务

在给出回答后，立即从暂停的确切点继续活跃的任务。除非旁问的回答揭示了阻塞项或需要重新考虑当前方案的原因（见边界情况），否则不需要请求许可。

## 边界情况

**未提供问题（`/aside` 后面什么都没有）：**
回复：
```
ASIDE: 未提供问题

你想了解什么？（提出你的问题，我会在不丢失当前任务上下文的情况下回答）

— 回到任务：[正在做的事情的一行描述]
```

**问题揭示当前任务可能存在的问题：**
在恢复前清楚标记：
```
ASIDE: [回答]

⚠️ 注意：这个回答暗示当前方案存在 [问题]。想在继续之前解决，还是按计划进行？
```
等待用户决定后再恢复。

**问题实际上是任务重定向（不是旁问）：**
如果问题暗示要改变正在构建的内容（例如 `/aside 实际上，让我们改用 Redis`），澄清：
```
ASIDE: 这听起来像是方向变更，而不仅仅是旁问。
你想要：
  (a) 仅作为信息回答，保持当前计划
  (b) 暂停当前任务并更改方案
```
等待用户回答 — 不要做假设。

**问题涉及当前打开的文件或代码：**
从实时上下文回答。如果文件在会话中已经读取过，直接引用。如果没有，现在读取（仅读取）并以文件:行号引用回答。

**没有活跃任务（调用 `/aside` 时无任何进行中的工作）：**
仍使用标准格式包装，保持响应格式一致：
```
ASIDE: [简要重述问题]

[你的回答]

— 回到任务：没有活跃任务需要恢复
```

**问题需要长回答：**
简洁地给出核心回答，然后提议：
```
以上是简短版。想在完成 [当前任务] 后获得更深入的解释吗？
```

**连续多个 `/aside` 问题：**
按顺序回答每一个。在最后一个回答后，恢复主任务。不要在一系列旁问中丢失任务状态。

**旁问的回答暗示需要代码更改：**
记录需要的更改但不要在旁问期间执行：
```
ASIDE: [回答]

📝 值得修复：[应该更改的内容]。除非你想现在处理，否则我会在当前任务后标记此项。
```

**问题模糊或过于含糊：**
问一个澄清问题 — 获取回答所需信息的最简短的问题。不要问多个问题。

## 输出示例

```
User: /aside fetchWithRetry() 实际做什么？

ASIDE: fetchWithRetry() 做什么？

fetchWithRetry()（src/api/retry.ts:12）最多尝试请求 3 次，
使用指数退避（250ms → 500ms → 1s）。仅对 5xx 响应和
网络错误重试 — 4xx 错误被视为最终结果，不重试。

— 回到任务：重构 src/middleware/auth.ts 中的认证中间件
```

```
User: /aside 我们正在采取的方案是线程安全的吗？

ASIDE: 当前方案是否线程安全？

不是 — src/cache/store.ts:34 中的共享缓存对象在没有锁的情况下被修改。
在并发请求下这是一个竞态条件。在单进程 Node.js 服务器中风险较低，
但在使用 worker threads 或集群时会是真正的问题。

⚠️ 注意：这可能影响我们正在构建的功能。想现在解决还是继续并在后续修复？
```

## 注意事项

- 旁问期间绝不修改文件 — 仅限只读访问
- 旁问是对话暂停，不是新任务 — 原始任务必须始终恢复
- 保持回答聚焦：目标是快速为用户解除疑惑，而非长篇大论
- 如果旁问引发了更大的讨论，先完成当前任务，除非旁问揭示了阻塞项
- 除非与任务结果明确相关，否则旁问不会保存到会话文件
