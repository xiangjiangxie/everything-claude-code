# 旁题命令

在任务进行中提问并获得即时、专注的回答 — 然后从中断的地方继续。当前任务、文件和上下文永远不会被修改。

## 何时使用

- 你在 Claude 工作时对某事感到好奇，不想丢失节奏
- 你需要对 Claude 正在编辑的代码进行快速解释
- 你想对一个决策获得第二意见或澄清而不偏离任务
- 你需要在 Claude 继续之前理解一个错误、概念或模式
- 你想问一个与当前任务无关的问题而不需要开始新会话

## 用法

```
/aside <你的问题>
/aside 这个函数实际返回什么？
/aside 这种模式是线程安全的吗？
/aside 我们为什么这里用 X 而不是 Y？
/aside foo() 和 bar() 有什么区别？
/aside 我们应该担心刚添加的 N+1 查询吗？
```

## 流程

### 步骤 1：冻结当前任务状态

在回答任何问题之前，在心中记下：
- 当前活跃的任务是什么？（正在处理什么文件、功能或问题）
- 调用 `/aside` 时正在进行什么步骤？
- 接下来要发生什么？

在旁题期间不要触及、编辑、创建或删除任何文件。

### 步骤 2：直接回答问题

以最简洁但仍完整有用的形式回答问题。

- 先给出答案，而非推理过程
- 保持简短 — 如果需要完整解释，提议在任务完成后深入讨论
- 如果问题是关于正在处理的当前文件或代码，精确引用（文件路径和行号，如相关）
- 如果回答需要读取文件，读取它 — 但仅读取，永不写入

响应格式：

```
旁题：[简要重述问题]

[你的回答]

— 回到任务：[正在做什么的一行描述]
```

### 步骤 3：恢复主任务

给出回答后，立即从暂停的确切位置继续活跃任务。除非旁题的回答揭示了阻塞问题或需要重新考虑当前方法的原因（见边界情况），否则不要请求恢复许可。

## 边界情况

**未提供问题（`/aside` 后面没有内容）：**
回复：
```
旁题：未提供问题

你想知道什么？（提出你的问题，我会在不丢失当前任务上下文的情况下回答）

— 回到任务：[正在做什么的一行描述]
```

**问题揭示了当前任务的潜在问题：**
在恢复前清楚地标记：
```
旁题：[回答]

⚠️ 注意：此回答表明当前方法存在 [问题]。想在继续之前解决这个问题，还是按计划继续？
```
等待用户决定后再恢复。

**问题实际上是任务重定向（不是旁题）：**
如果问题暗示要改变正在构建的内容（例如 `/aside 实际上，让我们改用 Redis`），澄清：
```
旁题：这听起来像是方向变更，而不只是旁题。
你想要：
  (a) 仅作为信息回答并保持当前计划
  (b) 暂停当前任务并更改方法
```
等待用户回答 — 不要做假设。

**问题是关于当前打开的文件或代码：**
从实时上下文回答。如果文件在会话中较早时已读取，直接引用。如果没有，现在读取（只读）并用文件:行号引用回答。

**调用 `/aside` 时没有活跃任务（什么都没在进行）：**
仍然使用标准格式以保持响应形状一致：
```
旁题：[简要重述问题]

[你的回答]

— 回到任务：没有活跃任务需要恢复
```

**问题需要长篇回答：**
简洁地给出核心答案，然后提议：
```
这是简短版本。想在我们完成 [当前任务] 后深入了解吗？
```

**连续多个 `/aside` 问题：**
依次回答每一个。在最后一个回答后，恢复主任务。不要在一系列旁题中丢失任务状态。

**旁题回答暗示需要代码更改：**
记下需要的更改但不在旁题期间执行：
```
旁题：[回答]

📝 值得修复：[应该更改什么]。除非你想现在解决，否则我会在当前任务完成后标记此问题。
```

**问题模糊或太笼统：**
问一个澄清问题 — 获取回答所需信息的最简短问题。不要问多个问题。

## 示例输出

```
用户：/aside fetchWithRetry() 实际做什么？

旁题：fetchWithRetry() 做什么？

fetchWithRetry()（src/api/retry.ts:12）最多尝试请求 3 次，使用指数退避
（250ms → 500ms → 1s）。它只在 5xx 响应和网络错误时重试 — 4xx 错误
被视为最终结果，不会重试。

— 回到任务：重构 src/middleware/auth.ts 中的认证中间件
```

```
用户：/aside 我们采用的方法是线程安全的吗？

旁题：当前方法是线程安全的吗？

不是 — src/cache/store.ts:34 中的共享缓存对象在没有锁的情况下被修改。
在并发请求下这是一个竞态条件。在单进程 Node.js 服务器中风险较低，
但在使用 worker threads 或集群时会成为真正的问题。

⚠️ 注意：这可能影响我们正在构建的功能。想现在解决还是继续，在后续修复？
```

---

## 注意事项

- 旁题期间永远不要修改文件 — 仅只读访问
- 旁题是对话暂停，而非新任务 — 原始任务必须始终恢复
- 保持回答聚焦：目标是快速解除用户的疑惑，而非进行演讲
- 如果旁题引发了更大的讨论，先完成当前任务，除非旁题揭示了阻塞问题
- 旁题不会保存到会话文件，除非与任务结果明确相关
